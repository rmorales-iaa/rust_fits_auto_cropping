# Scientific Fits Engineering

Work and respond in English. Apply this contract to scientific FITS projects.

## Project contract
- Documentation belongs in `input/doc/`; maintain a root `README.md` for remote repository readers.
- Runtime configuration belongs in `input/`. Tool-required manifests and lockfiles (for example Cargo.toml and Cargo.lock) remain in their standard locations; document exceptions.
- This project's FITS-file processing uses a bounded Rayon pool. `processing.threads` defaults to 4; `0` requests all logical CPUs available to the process, subject to memory and CPU limits. Record and report the effective worker count.
- The yearly calibrated-data script defaults to years 2002–2026 and takes a sequence of years (positional, `--years` comma/space list or repeated `--year`), run in the order given with repeats run once; year ranges are not accepted. It explicitly sanitizes each selected year's dedicated `science_calibrated/` output root before processing; explain this deletion clearly and preserve sibling source/calibration directories.
- Derived data belongs in `output/` by default. An explicitly selected output directory becomes the output root. Isolate each run under `runs/<run-id>/images/` by default, with optional previews, reports and its ISO-named activity log together; explicit `--flat-output` mode may write science images directly into a fixed user-selected root while keeping previews in `previews/`. `--sanitize-output` may clear a validated dedicated output root only when explicitly selected. Do not create per-input completion manifests. Binary mask/reason-mask trees may be used as transient write/verification sidecars but must be removed before final reports and process exit; reports must not point to them. Validate the output root, managed paths and relative components; reject symlinked paths and input/output overlap before product writes. Preserve older outputs and unrelated root files unless explicit sanitation is requested. Store build state under ignored `output/.state/`.
- Implement a central structured activity logger. Use UTC ISO-8601 timestamps in every entry and ISO-derived safe filenames, e.g. `2026-10-27T10-30-00.123Z_<run-id>.jsonl`. Record invocation, configuration hash, source/version, input identity, stages, decisions, warnings, failures, outputs, durations, resources and completion. Include administrative work when practical. Never record secrets. Flush on orderly termination and report logging failures.
- Keep each substantial class or Rust struct with its implementation in one focused, documented file. Small companion enums/types may remain together. Prefer files below approximately 300 lines; split by responsibility, not arbitrary line count.
- Maintain comprehensive CLI help, README, architecture, algorithm, configuration and validation documentation, and a .gitignore excluding generated products, raw local data, credentials and caches.
- For pixel-artifact detection, derive classification evidence from image samples and mask geometry, not descriptive header cards. Header/WCS metadata limitations must be reported but cannot alone skip a decodable image; when a limitation blocks safe crop geometry, apply accepted detections as a dimension-preserving mask. Never repair or normalize source header cards. Same-width placeholders may be used only in the parser's temporary in-memory view for malformed non-structural cards; annotate them, keep the original 80-byte cards exactly in generated FITS headers, and process the pixels. Require valid structural layout fields needed to locate/decode samples. In normal runs, create one image entry per discovered FITS input under `images/` by default or at the output root in `--flat-output` mode: accepted products are generated, while genuinely unreadable structural inputs and unsupported images are annotated and preserved as symlinks to canonical sources. Never write provenance through symlinks. Dry-run intentionally produces no image entries. Generated science products copy the source header cards verbatim (only NAXIS1/2, CRPIX*, existing LTV1/2, a needed BLANK and CHECKSUM/DATASUM change) and add program information only as `MO_` keywords (`MO_PROG`, `MO_DATE`, `MO_ACT`, `MO_CROP`, ...); record run version/time in summary and logs.
- PNG previews are opt-in and must not be generated unless requested. Crop comparison previews must estimate an independent ZScale interval from the exact final crop samples; source and crop display stretches may differ. Preview resampling is display-only and must not alter FITS samples. Preview files drop the FITS extension (`frame.fits` -> `frame.png`) unless two inputs in one directory would share that name, in which case both keep the full name.
- Carry the parsed FITS source snapshot used for detection through product writing and verification. Do not reopen a mutable source path to obtain output pixels or expected retained values; this can make the action differ from the classified frame. Keep the unchanged-source symlink path separate.
- Hash eligible source bytes during parsing through the same open handle, including FITS padding skipped by forward seeks; record the digest in the per-image report.
- Keep reports explicit about decisions versus products: proposed exclusions and applied exclusions are separate counts; dry-run proposals must never be counted as completed clipping. Crop geometry sacrifices and original undefined pixels need separate accounting before any metric is labeled valid-area loss. A larger proposal mask alone is not an improvement.
- For detector-tolerant rectangle cropping, make residual flagged-pixel fraction an explicit validated heuristic, keep original undefined pixels as hard exclusions, bound and report search work, and distinguish retained detector flags from excluded artifacts. Do not describe detector flags or a provisional ceiling as ground truth or calibrated contamination probability; verify selected samples, exact NAXIS/WCS, reason-plane codes and preview geometry independently.
- This project uses a tracked `input/program-version.txt` template and local ignored `output/.state/program-version.txt` counter. Cargo package recompilations advance the three-part base-100 version. Check current branches/remotes before authorized merge/push; never invent a remote URL.

## Scientific improvement reviews

In rust_fits_auto_cropping, read the project memory, latest scientific audit and active scientific improvement plan under `input/doc/` before extending algorithms. Historical plans and passing tests are not proof that every stated invariant is implemented. Distinguish proposed artifact pixels, accepted exclusions, original undefined samples, geometric sacrifices and independently labeled valid/invalid science. Optimize valid retention and artifact removal under declared risk and source-preservation limits; never maximize mask size as a proxy for quality. Freeze data splits, estimands, tolerances and meaningful improvement thresholds before tuning. A planning review ends with an auditable plan and explicit unresolved implementation/data gates, not a scientific certification. Probe the shipped heuristics with deterministic synthetic counterexamples before redesigning. Reject reference rules that let unrelated interior pixels change border decisions (for example a maximum-dispersion reference). Treat variance evidence as two-sided, because flat-divided calibrated borders are noisier, not quieter. Never let raw undetrended correlation alone admit a candidate. Compare every crop outcome against the mask and bounding-box-plus-mask alternatives so dominated actions are visible. Derive thresholds from a registered null false-alarm rate, not hand tuning. Crop-mode fallbacks must not discard detections when a dominating action exists: `bbox_mask` removes every accepted flag with no valid-pixel loss. `crop_masked` allows internal BLANK/NaN only as an explicit opt-in. Keep new detectors opt-in with their own algorithm identity until they pass labelled real-data gates, unless the user explicitly decides otherwise (decision D5 made v2 the default before G4; a default is not a validation claim, and the previous detector must stay selectable).

## Work cycle
1. Explore existing code and Git state before editing. Preserve unrelated work.
2. Before complex work, save a phased implementation plan in `input/doc/` with assumptions, acceptance criteria and tests. When the user asks for implementation, continue from that plan, track evidence against each phase and update its status; do not stop after planning.
3. Specify units, coordinates, time scales, numerical precision, uncertainty, failure modes and a reproducible validation dataset. Cite primary references; never call an algorithm scientifically validated without evidence.
4. Implement the smallest complete phase. Preserve originals, use atomic output writes and fail conservatively on ambiguous scientific decisions.
5. Apply efficient I/O, allocation reuse and bounded parallelism where safe and beneficial. Benchmark serial and parallel paths; preserve deterministic science results and cap memory. Do not parallelize unsafe library handles.
6. Add substantial unit, integration, property, edge-case, synthetic-science and regression tests. Include independent reference checks, serial/parallel equivalence and end-to-end error handling.
7. Run relevant tests and quality checks, inspect the diff, and automatically commit each verified coherent change to the local repository. Initialize Git if absent. Include documentation and tests; exclude secrets, raw data, logs and outputs. Do not push or rewrite history without explicit authorization. Never invent author identity; report a genuine commit blocker.
8. Before declaring implementation complete, map every plan requirement to code and validation evidence. Report incomplete or deferred items honestly, along with commit and output locations.
